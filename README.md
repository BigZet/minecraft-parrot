# Viewer Parrots

Minecraft-мод (Fabric): персональный попугай-зритель с постоянной идентичностью, характером
и управляемым поведением. Полное ТЗ — [viewer_parrots_technical_spec.md](viewer_parrots_technical_spec.md).

## Зафиксированные версии (M0)

| Компонент | Версия |
|---|---|
| Minecraft | 1.21.1 |
| Java | 21 (Temurin 21.0.12) |
| Fabric Loader | 0.19.5 |
| Fabric API | 0.116.17+1.21.1 |
| Yarn mappings | 1.21.1+build.3 |
| Fabric Loom | 1.17.20 |
| Gradle | 9.5.1 (wrapper) |

Все версии закреплены точными значениями в `gradle.properties`; динамические `+`/`latest` не используются.

## Сборка

```bash
./gradlew build
```

Готовый JAR — `build/libs/viewerparrots-<version>.jar`.

## Запуск в разработке

```bash
./gradlew runClient   # клиент с модом
./gradlew runServer   # dedicated server
```

Клиент работает в `run/`, dedicated server — в `run/server/` (разные каталоги, иначе они дерутся
за мир и `logs/latest.log`). Mojang EULA в `run/server/eula.txt` уже принят.

### Временные команды приёмки M0

Уровень прав 3. Будут заменены полным набором `/viewerparrot …` из раздела 6 ТЗ на этапах M2–M3.

```
/viewerparrots-m0 spawn <RED_BLUE|BLUE|GREEN|YELLOW_BLUE|GRAY>
/viewerparrots-m0 dance on|off
/viewerparrots-m0 info
/viewerparrots-m0 tp <измерение>
```

## Результаты M0

Проверено на dedicated server 1.21.1.

| Проверка | Результат |
|---|---|
| Сборка и запуск клиента | проходит |
| Запуск dedicated server | проходит; серверная инициализация не тянет клиентские классы |
| Регистрация `viewerparrots:viewer_parrot` | проходит на обоих окружениях |
| Танец без jukebox | работает |
| Удержание места во время танца | работает |
| UUID при переносе между измерениями | сохраняется |

Выводы, влияющие на дальнейшие этапы:

1. **Танец не требует mixin и access widener.** `ParrotEntityModel.getPose()` вызывает
   `isSongPlaying()` виртуально, поэтому переопределения этого метода поверх tracked-флага
   `FORCED_DANCING` достаточно. Ванильное поле `songPlaying` не используется: оно сбрасывается
   в `ParrotEntity.tick()`, когда рядом нет проигрывающего jukebox.
2. **`Entity.teleportTo` создаёт НОВЫЙ Java-объект.** UUID при этом сохраняется, но ссылка на
   прежний объект становится недействительной — `LoadedEntityIndex` обязан обновляться после
   переноса (раздел 5.3 ТЗ).
3. **Tracked-состояние не переживает перенос между измерениями.** Флаг танца сбрасывается в
   `false`, потому что новый объект восстанавливается из NBT, а tracked data в NBT не входит.
   Контроллер должен либо переносить runtime-состояние явно, либо трактовать перенос как отмену
   временных действий — решение принимается на M3.
4. **Ванильные goals уводят попугая в полёт.** `FlyOntoTreeGoal` (приоритет 2) и `FollowMobGoal`
   (приоритет 3) вытесняются собственным goal с приоритетом 0 на время танца. Полный собственный
   набор goals остаётся задачей M3–M4.
5. Ошибка `No data fixer registered for viewer_parrot` в логе — диагностика только дев-окружения
   (`Util.getChoiceType` закрыт проверкой `SharedConstants.useChoiceTypeRegistrations`). В обычной
   игре её нет, её выдаёт любая модовая сущность.

Отложено по решению от 13 сентября 2026: приёмка в мультиплеере с двумя клиентами одновременно —
AC-08 (танец виден обоим клиентам) и AC-09 (второй клиент начинает tracking посреди танца и видит
текущую анимацию). Архитектурно требование уже выполнено — флаг танца живёт в `DataTracker` и
поэтому входит в начальный пакет данных сущности для каждого нового наблюдателя, — но фактическая
проверка требует двух клиентов и одного dedicated server в одном сеансе.

## Результаты M1

Домен, реестр, права, конфигурация и storage. Всё это чистая Java: пакет `domain` не зависит
от Minecraft, поэтому проверяется обычными unit-тестами без запуска игры.

```bash
./gradlew test
```

221 тест, покрывают требования раздела 15.1 ТЗ: валидацию identity, обе state machine,
границы cooldown и глобальные бюджеты, ёмкость реестра, JSON round-trip и схему,
контрольные суммы, replay журнала и аварийные сценарии.

Решения, принятые на этом этапе:

1. **Время внедряется как зависимость.** `GameClock` разделяет две шкалы: счётчик тиков для
   cooldowns и deadlines (игровое время стоит вместе с сервером) и календарное UTC для
   `createdAt`/`updatedAt`. Тесты используют управляемые часы, без `Thread.sleep`.
2. **Граница cooldown строгая:** запрещено при `tick < deadline`, разрешено ровно при
   `tick == deadline`. Поэтому нулевой cooldown у `sit` не запрещает ничего.
3. **Разбор JSON строгий.** Штатный `JsonParser` не подошёл: он молча оставляет последний
   из дублирующихся ключей. Свой разбор отвергает дубликаты, неизвестные поля, неизвестные
   константы enum и не-finite числа — каждый раз с JSON path.
4. **Контрольные суммы журнала** считаются по канонизированному представлению: ключи
   сортируются по code point, не по UTF-16 code unit. Разница видна на эмодзи, и правило
   закреплено отдельным тестом.
5. **Ёмкость** считает `PRESENT` и `MISSING` с ожидаемым UUID, а также незавершённые
   резервы под spawn. `DEAD` и `REMOVED` слот освобождают. Резерв берётся до записи на диск,
   поэтому конкурирующие `create` не могут превысить лимит.

Добавлен пакет `io.github.viewerparrots.json`, которого нет в структуре раздела 3.2:
строгий разбор нужен и конфигурации, и storage, а класть его в один из них означало бы
зависимость config от storage.

## Результаты M2

Домен соединён с игрой: NBT-маркер сущности, индекс загруженных, арбитраж поколений,
durable-операции жизненного цикла и команды `/viewerparrot` (алиас `/vp`).

```
/viewerparrot setstreamer <player> | streamer
/viewerparrot create <viewerId> <имя> | remove <viewerId>
/viewerparrot rename <viewerId> <имя> | trait <viewerId> <trait>
/viewerparrot respawn <viewerId> | reconcile <viewerId>
/viewerparrot info <viewerId> | list [страница]
/viewerparrot save | status
```

Порядок durable-операции неизменен: резерв слота → `PREPARE` → spawn → `COMMIT` → включение AI.
До `COMMIT` новая сущность существует с выключенным AI и команд не принимает. При любом отказе
после `PREPARE` пишется `ABORT`, а подготовленная сущность удаляется. `remove` фиксирует
надгробие **до** удаления сущности: при падении между шагами выгруженную копию отвергнет
валидатор.

Проверено на dedicated server: запуск, загрузка реестра, `status`, `list`, `streamer`, `save`
с атомарной заменой снимка, отказы `TARGET_NOT_CONFIGURED`, `VIEWER_NOT_FOUND` и
`INVALID_ARGUMENT` с локализованными сообщениями, алиас `/vp`.

Решения и находки этапа:

1. **`viewerId` объявлен как `string()`, а не `word()`.** Раздел 4.1 разрешает в нём символ `:`,
   но Brigadier не принимает `:` в неквотированном слове — такие id нельзя было бы ввести.
   С `string()` обычные id по-прежнему пишутся без кавычек, а `"ns:viewer"` — в кавычках.
2. **Маркер живёт в собственном namespace NBT** и не пересекается с ванильными полями попугая.
   Повреждённый маркер не ломает загрузку чанка: сущность остаётся неопознанной и отвергается.
3. **Сущность без маркера удаляется.** Это видно вживую: тестовые попугаи, созданные на этапе M0
   прежней отладочной командой, при первом же запуске M2 были отвергнуты с причиной
   «нет маркера реестра» — то есть `/summon` без записи реестра зрителя не создаёт.
4. **Смерть применяется в памяти сразу, журнал пишется следом.** Смерть — факт, который нельзя
   отменить из-за ошибки I/O; сбой записи переводит мод в degraded, но не «оживляет» попугая.
5. **Режим degraded вместо пустого реестра.** Повреждение данных или некорректный конфиг не
   прерывают запуск сервера, но запрещают изменения и останавливают AI собственных сущностей.

Не закрыто в M2: команды движения (`come`, `follow`, `sit`, `dance`, `scream`) — это M3, вместе
с очередью действий и таймерами. До тех пор танец переключается вручную командой
`/viewerparrots-m0 dance <viewerId> on|off`. Путь `create` целиком требует онлайн-стримера,
поэтому проверен только до отказа `TARGET_NOT_CONFIGURED`; полная проверка — в игре.

## Результаты M3

Игровые действия, cooldowns, лимиты и события. Временная команда `/viewerparrots-m0` удалена —
танец стал настоящим, с таймером и восстановлением прежнего намерения.

```
/viewerparrot come <viewerId> | follow <viewerId> | sit <viewerId>
/viewerparrot dance <viewerId> | scream <viewerId>
```

Порядок проверок из раздела 7 соблюдается буквально и живёт в одном месте —
`ParrotCommandService`:

```
права → существование → готовность хранилища → состояние жизненного цикла →
target → переход поведения → глобальный лимит → cooldown → выполнение
```

Порядок здесь не украшение. Отказ по правам не должен расходовать глобальный бюджет,
а ошибка валидации — cooldown. Cooldown списывается ровно в момент принятия действия,
включая LAZY-отсрочку, и последующая отмена его не возвращает.

Решения этапа:

1. **`ParrotRuntime` не сохраняется.** После рестарта восстанавливается только намерение
   из реестра; незавершённые `DANCING`, `RETURNING` и LAZY-задания отменяются, cooldowns
   сбрасываются. Ссылок на сущности здесь нет — они живут в `LoadedEntityIndex` и
   удаляются при выгрузке.
2. **LAZY задерживает только движение.** `sit` выполняется немедленно из любого состояния,
   как требует раздел 10. После задержки состояние проверяется заново, но cooldown второй
   раз не списывается.
3. **Бюджеты соблюдаются буквально:** не больше 2 переносов за тик глобально, пересчёт
   маршрута не чаще раза в `repathTicks` на попугая.
4. **Ошибка поведения изолируется.** Сбой одного попугая не останавливает остальных;
   после трёх подряд ошибок его автономное поведение отключается до перезапуска.
5. **Дедупликация по `commandId`** держит результат 5 минут при пределе в 1024 записи.
   Повторная доставка того же запроса не выполняет действие второй раз; через рестарт
   дедупликация не гарантируется.

Два сознательных отступления от ТЗ, принятые по результатам проверки в игре:

- **Длительность танца 200 тиков вместо 100** (раздел 11). Пять секунд оказались слишком
  коротким танцем. Значение совпадает с cooldown, поэтому повторить танец можно ровно
  в момент его окончания.
- **Спасение из пустоты.** Раздел 9.6 разрешает не защищать от void, и попугай трижды
  погиб, выпав из мира: при танце над дырой, стоя у обрыва и следуя за стримером.
  Зритель должен быть постоянным, поэтому в режиме, блокирующем обычный урон, упавший
  ниже дна мира переносится к стримеру вместо гибели. Это отступление от буквального
  чтения AC-16.

Не закрыто в M3: traits `COWARD`, `LAZY`-idle и `LOUD` как автономное поведение,
idle-scheduler и события `ParrotCreated`/`ParrotRemoved` от сервиса жизненного цикла —
это M4. Приёмка AC-05–10 и AC-22 требует двух клиентов и отложена вместе с AC-08 и AC-09.

## Структура

- `src/main` — common/server код; не должен ссылаться на клиентские классы.
- `src/client` — клиентский код (рендер, презентация), отдельный source set через `splitEnvironmentSourceSets()`.
- `src/test` — unit-тесты; JUnit 5, без Minecraft.

Слои: `domain` (без зависимостей от игры) → `registry`, `behavior`, `ratelimit`, `service`,
`config`, `storage` → `entity`, `command`, `client` (только они знают о Minecraft).
